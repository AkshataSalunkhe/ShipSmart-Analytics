# ShipSmart Logistics -- Pricing & Retention Analytics

A self-contained, end-to-end pricing-analytics project built around one fictional B2B
freight/parcel shipper, "ShipSmart Logistics." It's a personal project for practicing
and showcasing the ML side of pricing work: estimating what customers are actually
willing to pay, grouping accounts by behavior, flagging who's about to leave, testing
a price change properly before rolling it out, and forecasting where revenue is headed.
Everything runs on **synthetic data**, generated by a documented, realistic simulator --
not scraped or copied data, and no external dataset dependency.

**Live artifacts:**
- `dashboard/dashboard.html` -- open in any browser. A single self-contained page summarizing all five modules (no server needed).
- `notebooks/*.ipynb` -- six pre-executed Jupyter notebooks with real outputs (tables, metrics, charts) already rendered, so they're readable without re-running anything.
- `scripts/*.py` -- the same notebook content as plain, diff-friendly Python (percent-cell format, `# %%`), which is what actually generated the notebooks and all figures/data.

## What this covers

Five linked notebooks, each standing on its own but sharing one customer base:

1. A price-response ("what will this customer pay?") model, turned into a per-segment demand curve and a price recommendation.
2. A behavioral clustering pass that checks whether accounts naturally group the way sales already tiers them.
3. A model that flags which accounts are likely to go quiet in the next few months, before it happens.
4. A randomized test of a proposed price change, with a guardrail check before deciding whether to ship it.
5. A monthly revenue forecast per customer group, comparing a few modeling approaches honestly rather than assuming the fanciest one wins.

A short HTML dashboard ties the five together for a non-technical read; the notebooks
carry the full methodology for anyone who wants to see the work.

## The business scenario

ShipSmart quotes prices to shippers across four commercial tiers (Enterprise,
Mid-Market, SMB, Occasional). Every quote either gets accepted or not, at a price set
relative to a competitor's price for the same shipment. The simulator (`scripts/simulate.py`)
encodes segment-specific price sensitivity, service-level effects, and contract-type
effects, then **every downstream model only ever sees the observable outcome (accepted
or not, revenue), never the hidden simulation parameters** -- exactly like a real data
scientist would only see behavior, not the customer's "true" price elasticity.

## How to run it yourself

```bash
pip install pandas numpy scikit-learn matplotlib seaborn scipy
cd scripts
python3 gen_01_data.py          # generates data/*.csv (~93k quotes, ~3.5s)
python3 gen_02_segmentation.py
python3 gen_03_wtp.py
python3 gen_04_churn.py
python3 gen_05_ab_testing.py
python3 gen_06_forecasting.py
python3 build_all_notebooks.py  # rebuilds notebooks/*.ipynb with fresh outputs
cd ../dashboard && python3 build_dashboard.py
```

Each `gen_*.py` script is independently runnable (`python3 gen_03_wtp.py`) and is also
valid input to `build_all_notebooks.py`, which executes it cell-by-cell and captures
real stdout/figures into the `.ipynb`. There's no dependency on Jupyter itself being
installed to *produce* the notebooks -- only to open them afterwards (or just read them
on GitHub/VS Code, which render pre-executed notebooks fine without a kernel).

## Module-by-module summary

**1. Data generation.** ~3,000 customers, ~92,500 historical quotes (2019-2026), a
leakage-safe churn-label design (features strictly before a cutoff, label strictly
after), and a monthly revenue panel by segment.

**2. Segmentation.** RFM-style behavioral features (tenure-normalized to avoid
confounding "long-tenured" with "high-value"), K-Means at k=4, validated against the
already-assigned commercial tier (Adjusted Rand Index 0.44 -- meaningful agreement,
not identity). ~26% of accounts sit in a cluster dominated by a different tier than
their assigned one -- flagged as tier-review candidates.

**3. Willingness-to-pay.** A gradient-boosted classifier predicts quote acceptance
from price-vs-competitor ratio plus shipment/customer context (time-based train/test
split, AUC 0.605, calibration-checked). Sweeping price at inference time yields a
demand curve and a revenue-maximizing price per segment -- **capped at the edge of
observed price variation**, so the model doesn't recommend prices in territory it's
never seen (a real failure mode of naive ML-based pricing).

**4. Churn prediction.** Predicts, from a fixed cutoff, which active accounts go quiet
over the next 6 months (AUC 0.83, PR-AUC 0.32 against a 10.6% base rate). A decile
analysis shows the top 20% highest-risk accounts capture 62% of actual churners --
the number a retention team would actually act on.

**5. A/B pricing test.** Randomizes (by customer, stratified by segment) the WTP
model's recommended price against business-as-usual, with a pre-registered guardrail
(don't ship if acceptance rate drops >3 points). Result: revenue per quote up 9.5%
(p=0.025) but acceptance rate down 4.7 points (p<0.001), **breaching the guardrail in
3 of 4 segments**. Recommendation is to ship only where the guardrail holds
(Enterprise) and re-test a smaller move elsewhere -- a deliberately non-trivial,
metric-tension outcome rather than a clean "the model was right, ship it everywhere."

**6. Forecasting.** Compares a seasonal-naive baseline, a trend+seasonal linear
regression, and a lag-feature gradient-boosted model (recursive/walk-forward, since
`statsmodels`/`prophet` weren't installable in the build environment) on a 6-month
backtest per segment. Honest finding: **with only ~4 years of monthly history, neither
fitted model reliably beats the naive baseline**, and the linear model is actively
unstable on the smallest segment. The writeup recommends leaning on the naive forecast
today and revisiting with more history, rather than shipping a fancier model that
isn't actually more accurate.

## Design decisions worth explaining out loud

- Model complexity vs. data volume (forecasting module) -- the fancier model doesn't
  automatically win, and the notebook shows the math on why.
- Extrapolation risk when a model recommends a price it's never actually seen tested
  (WTP module), and a concrete way to cap it.
- Why a statistically significant revenue bump isn't automatically a "ship it" decision
  once it trades off against a guardrail metric (A/B module).
- Leakage-safe label design -- features cut off before the label window starts (churn module).
- Checking a data-driven grouping against the existing business tiers instead of assuming
  either one is automatically "correct" (segmentation module).

## Limitations / what's out of scope

- **Full network-wide price optimization** (jointly optimizing prices across the whole
  book of business, subject to volume and competitiveness constraints, e.g. via linear
  programming) was scoped out of this project in favor of going deeper on the price-
  response, experimentation and forecasting pieces. The price-recommendation step is a
  per-segment, per-shipment simplification, not a full constrained solver.
- No `statsmodels`/`prophet`/`xgboost`/`shap` -- the build environment's package index
  was unavailable, so forecasting uses lag-feature gradient boosting + linear
  trend/seasonal regression instead of ARIMA/exponential smoothing, and feature
  importance uses permutation importance instead of SHAP. Swapping either in on a
  machine with full package access is a small, contained change.
- All data is synthetic. The realism is in the *structure* of the problems (leakage-safe
  labels, time-based splits, extrapolation guardrails, guardrail-vs-headline-metric
  tension) rather than in any specific number matching a real business.

Python, pandas, numpy, scikit-learn (K-Means, HistGradientBoosting, LogisticRegression,
